## 1. 估算前提与假设

在展开计划前，请先确认以下假设是否成立，它们直接决定所有数字的可信度：

| 编号 | 假设 | 说明 |
| --- | --- | --- |
| A1 | 1 人日 = 8 小时**有效编码时间** | 不含会议、上下文切换、需求讨论 |
| A2 | 开发者具备中等以上 Rust 熟练度 | 但 `russh`、`ratatui`、终端仿真三块存在学习曲线，已在 M0 / M1 中单独计入学习成本 |
| A3 | 单人开发，无并行人力 | 若为多人，M3/M4 可与 M5 并行，见 §6 |
| A4 | 需求不再发生结构性变更 | 若中途改架构（如换掉 daemon 模型），需整体重估 |
| A5 | 估算**不含返工与缓冲** | §7 给出 +30% 缓冲建议，请勿直接把本文件的人日当作承诺工期 |
| A6 | 跨平台成本已分摊进各里程碑 | CI matrix（Linux gnu/musl、macOS x86/arm、Windows）与平台差异调试不再单列 |
| A7 | 不实现 SSH 服务端、不做 GUI | 见需求文档 §7 Out of Scope |

**优先级与"可停止点"说明**：M2 结束是本项目的**首个完整可交付点**——此时人类能用 TUI 日常运维，AI 能用 CLI 完整操作。M3/M4/M5 是增值层，可以按需裁剪或延后。

> 双渲染器与 12 类退出码、风险三档引擎（shell 词法切分 + 分段判定 + 内置规则集 +

> SQLite 审计（脱敏先行 + 输出归档 + 保留期与体积上限）、OS 钥匙串 + 主密码 vault 双后端凭据。
>
> 测试：**75 条**（终端 23 + 会话 12 + 风险 14 + 审计 3 + 凭据 5 + exec 12 + 契约 11 等），
> `cargo clippy --workspace --all-targets` 零警告。契约测试进程内起完整 daemon（假传输层），
> 覆盖 AC-4 ~ AC-8。
>
> 实现期对计划的三处偏离，已同步进架构文档：
> 1. **IPC 后端改为 loopback TCP + 令牌**（原计划 UDS / Named Pipe）——见 §9 说明。
> 2. **russh 必须启用 crypto backend**（`ring`），因此引入 C 依赖，与 NFR-11 的
>    「纯 Rust 优先」有冲突 —— 见架构文档 §9 备注。
> 3. **审计库用 `rusqlite bundled`**（SQLite 源码随包编译，需 C 工具链），换取
>    「单二进制、不依赖系统 SQLite」——与 ring 同属受控的 C 依赖，见架构文档 §9。
>
> **M2 已真机验证（2026-10-24）**：在真实 Debian / aarch64 主机（密码认证 + TOFU）上
> 完整跑过一轮——会话开关与就绪、双模式 exec（shell 哨兵 / exec channel）、屏幕读取、
> 按键注入、风险三档（auto / confirm + 令牌闭环 / deny）、审计回溯，全部通过。
>
> 真机一轮揪出四个 mock 测不出来的缺陷，均已修并补了回归：
> 1. **未知 SSH 通道消息被当成 EOF**（`Success` / `WindowAdjust`）→ 会话刚连上就断开；
> 2. **EOF 后立即退出循环** → 拿不到随后到达的 `exit-status`，`exit_code` 恒为 null（AC-4 不成立）；
> 3. **哨兵回显噪声剥不干净**：bash 会先裸回显输入、再由 readline 重绘一遍命令行，
>    只剥首行或末行都会留下噪声；
> 4. **keyring 未启用平台后端 feature** → 静默退化成 mock 后端（写入成功、读取永远为空）。
>
> **M2 遗留风险**：`clear` 刷屏、改写 `PS1`、超长命令折行等极端形态仍未实测；
> `keyboard-interactive` / 2FA 未实现（M5）。

> **M3**（9 人日）：广播模式（daemon 广播态 + `ai broadcast *` + TUI `Alt+B`/`Alt+M`）、

## 3. 里程碑详解

### M0 · 骨架与连通（12 人日）

**目标**：把"能从零连上一台机器并看到字节流"这条最短路径打通，同时把工程地基（workspace、CI、配置层、进程模型）一次性立好。

| 任务 | 内容 | 人日 |
| --- | --- | --- |
| W0.1 | Cargo workspace 初始化，8 个 crate 骨架与依赖方向约束（可用 `cargo-deny` / CI 检查拦截反向依赖） | 1.0 |
| W0.2 | `sh0-cli` 命令路由骨架：`daemon run/stop`、`tui`、`ai`、`host`、`config` 顶层分支 | 1.0 |
| W0.3 | `sh0-store` 配置层：TOML schema 定义、`dirs` 路径解析（三平台）、版本号字段 | 1.5 |
| W0.4 | `sh0-ssh` 连接与认证：密码、私钥文件（OpenSSH / PEM）、passphrase、ssh-agent | 3.0 |
| W0.5 | `sh0-ssh` known_hosts 校验与 TOFU 首次确认流程 | 1.0 |
| W0.6 | daemon 进程模型：后台 spawn / attach 已有实例、PID 文件、优雅退出、`tracing` 日志 | 2.0 |
| W0.7 | `sh0-ipc` v1：传输层抽象 + **loopback TCP + 令牌**后端（UDS / Named Pipe 留待后续替换），ping/echo 打通 | 1.5 |
| W0.8 | 最小 TUI：单视图直接渲染原始字节流（**不做终端仿真**），验证键盘→远端回环 | 1.0 |

**验收标准**
- `sh0` 首次运行自动拉起 daemon 并显示终端视图，能敲命令看到回显。
- `sh0 daemon stop` 后会话全部断开且日志完整落盘。
- `sh0 ai session list --json` 返回合法 JSON 信封（空数组）。
- CI：Linux(gnu/musl) / macOS(arm/x86) / Windows 五档产物均能启动并打印版本。

**产出**：workspace 骨架、`README.md`、CI 流水线、可手动连通的二进制。
**主要风险**：Windows Named Pipe 权限与 UDS 抽象不统一 → 提前在 W0.7 做双平台最小验证，不要拖到 M2。

| W2.9 | 确认机制：有人值守走 TUI 弹窗；无人值守返回 `needs_confirmation` + 一次性 token | 1.5 | FR-7.4 |
| W2.10 | 速率限制与主机 `risk_cap` 上限 | 1.0 | FR-7.6 / FR-7.7 |
| W2.11 | 错误码 → 退出码映射（12 类）+ 全子命令端到端契约测试 | 1.5 | FR-6.10 / NFR-10 |
| W2.12 | 凭据存储：OS 钥匙串优先 + 主密码加密回落；确保配置无明文 | 1.5 | FR-1.4~FR-1.7 |

**验收标准**（2026-10-24：全部达成，由 `crates/sh0-cli/tests/contract.rs` 的 11 条契约测试守护）
- **AC-4** ✅：`sh0 ai exec --host X --cmd "uname -a" --json` 返回合法 JSON，含 stdout/stderr/exit_code/duration_ms。
- **AC-5** ✅：`rm -rf /` 类命令无论 actor 一律 `deny`，审计留痕（连 `--yes` 也拦）。
- **AC-6** ✅：`confirm` 档在无人值守模式返回 `needs_confirmation` + token，带 token 二次调用可通过
  （令牌单次消费，重放报 `invalid_args`）。
- **AC-7** ✅：配置目录内 grep 不到任何明文密码（vault 密文 + `SH0_DISABLE_KEYRING` 下的确定性验证）。
- **AC-8** ✅：AI 与 TUI 操作同一批会话，双方动作都出现在同一份审计日志中。
- 契约测试覆盖全部 P0 子命令 × 成功/失败/需确认三条路径。

**实现与计划的偏差**
1. **`exec` 双模式同时落地**（原计划只把 exec channel 当备选）：默认走 shell 哨兵模式
   （复用交互 shell、拿得到上下文），`--mode exec` 走独立 SSH channel（stdout/stderr 天然分离、
   退出码精确，但没有交互上下文）。AI 可按场景选，`NFR-10` 的契约测试两种模式都覆盖。
2. **凭据后端**：钥匙串优先（macOS Keychain / Windows 凭据管理器 / Linux Secret Service），
   拿不到或用户禁用时回落到主密码 vault（Argon2id + ChaCha20-Poly1305）。
   `SH0_DISABLE_KEYRING=1` 可强制走 vault（测试用它保证确定性）。
3. **TUI 确认弹窗**：`confirm.requested` 事件 → 模态框（y 批准 / 其它键拒绝），
   `confirm.resolved` 事件回写结果。与无人值守令牌共用同一份待确认表。

**产出**：完整的 AI CLI + 契约测试套件 + 审计报告能力。**此时项目已具备对外交付价值。**
**主要风险**：`exec` 依赖"哨兵回显"判断命令结束，遇到 `PS1` 被改写或命令本身回显特殊字符时会误判 → 建议 W2.4 同时预留 `exec` 走独立 exec channel（不复用 shell）的备选路径，后者更可靠但拿不到交互式上下文。

## 9. 开工前必须先定的两件事（M0 已定稿）

这两项在 M0 开工时已确定，对应需求文档 §11 的 OQ-6 与 OQ-1：

| 项 | 结论 | 理由 |
| --- | --- | --- |
| **命令名** | `sh0` | 与仓库同名、最短、便于 AI 反复调用时少敲字符 |
| **IPC 后端** | loopback TCP（127.0.0.1 随机端口）+ 一次性令牌 | 跨平台行为一致、tokio 原生支持、M0 不必和 Named Pipe 权限较劲；传输层已抽象，后续可换 |

**关于 loopback TCP 的取舍**：它仍满足「不对外可达」（只绑 127.0.0.1）与「本机鉴权」（首帧令牌握手），
但相比 UDS / Named Pipe 少了文件系统的权限保护，令牌落在 `runtime_dir/daemon.json`。
NTFS 上该文件继承用户目录权限，风险可接受；若要更严，M2 可换 UDS（Unix，支持 0600）
并给 Windows 的 Named Pipe 配 DACL。届时只需替换 `sh0-ipc::transport` 内部，协议与上层不动。
